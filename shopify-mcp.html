Setup guide

What this is

Once connected, you can ask Claude things like "find the Revel Aura sauna," "what's the status of GAF order #138892," or "look up the customer on that order" and it pulls live answers straight from our Shopify stores.

This includes customer personal data (names, emails, addresses). Use it for legitimate work only — don't export, forward or share customer details outside the business.

Before you start

  • A Claude account (claude.ai or the Claude desktop app). The free plan allows one custom connector; Pro/Team allow more.
  • Your personal connector link — it's in the same shared LastPass item you opened these instructions from. It looks like the link below, with your own code on the end.
https://shopify-mcp.josh-03c.workers.dev/c/YOUR-PERSONAL-CODE
Treat this link like a password. It lives in LastPass for a reason — anyone who has it has your access. Don't copy it into shared chats, emails or docs. If it ever leaks, tell Josh and he'll issue a new one in seconds.

Set it up claude.ai — web

  1. Open claude.ai and sign in. Click your name (bottom-left) → Settings.
  2. Go to Connectors (under "Customize"). Click Add custom connector.
  3. In Remote MCP server URL, paste your personal link. Leave the OAuth Client ID / Secret boxes empty.
  4. Click Add. You'll see "Shopify" appear in your connector list.
  5. Open any chat. Click the + (or the connectors/tools icon) → Connectors → switch Shopify on.
  6. Ask it something — see the examples below. Done.
The connector stays in your account, so you only do this once. Just toggle it on (step 5) in new chats where you want to use it.

Set it up Claude desktop app

Exactly the same flow: Settings → Connectors → Add custom connector, paste your personal link, leave OAuth blank, click Add. Then toggle Shopify on inside a chat.

Try these

"Search Gym and Fitness products for adjustable dumbbells and show the prices."
"Look up Revel order 189122 — what's in it, who ordered it, and has it shipped?"
"Find the customer jane@example.com on Gym and Fitness and show their recent orders."
"What's the current stock and price on the Revel Aura 2-person sauna?"

Tip: tell it which store you mean — "Gym and Fitness" (GAF) or "Revel". You can ask about either.

If something's not working

The connector won't add

Check the link is pasted in full and the OAuth fields are left blank. On a free plan with an existing custom connector, you may need to remove the old one or upgrade.

No Shopify tools show up in the chat

Make sure you toggled the connector on for that chat (the + → Connectors menu).

It says "unauthorized" or stops working

Your link may have been rotated or revoked. Message Josh and he'll sort it.

On a Team or Enterprise plan and can't add a custom connector?

Custom connectors may be locked at the organisation level. Ask Josh to approve it under Organization Settings → Connectors first, then retry.

Architecture & security

Cloudflare Workers MCP (Streamable HTTP) Shopify Admin GraphQL Read-only

1 Purpose

Give selected team members read-only access to Gym and Fitness and Revel Shopify data from inside Claude — products, orders, customers and more — without ever handing them a Shopify API key, and with the key fully managed centrally. The credential lives server-side; access is scoped per user and revocable in seconds.

The Worker is the only component that holds a Shopify credential. The client authenticates to the Worker with its own per-user token; the Worker then talks to Shopify with a store credential the user never sees. Two independent trust boundaries, joined in the middle.

Request lifecycle

  • 1. Inbound — Claude POSTs a JSON-RPC message. The user's token arrives as Authorization: Bearer <token> or in the URL path (/c/<token>).
  • 2. Authenticate — Worker resolves the token against USER_TOKENS → { name, stores[] }. Unknown/missing → 401.
  • 3. Dispatch — initialize / tools/list answered locally; tools/call checks the requested store is in the user's allowlist, then runs the handler.
  • 4. Mint & cache — handler fetches a Shopify token via client_credentials (cached in-isolate ~20h of its 24h life), then calls the Admin GraphQL API.
  • 5. Return — the response is shaped into a clean object and returned as MCP tool content.

5 Authentication model

Two boundaries

  • User → Worker. Each person gets a unique random token, stored as a key in the USER_TOKENS secret (a JSON map). The value records their display name and which stores they may reach.
  • Worker → Shopify. Per-store client_id/client_secret live as encrypted Worker secrets. The Worker mints short-lived shpat_ tokens on demand. No Shopify credential is ever sent to the client.

Why two token-delivery methods

claude.ai's custom-connector UI (confirmed June 2026) accepts only OAuth or no-auth — it cannot send a custom Authorization header. So the Worker also accepts the token as a capability URL (/c/<token>): the user pastes one URL, leaves OAuth blank, and the path segment is the credential. Claude Code and desktop config files use the cleaner bearer header.

// USER_TOKENS secret — bearer -> identity + store allowlist
{
  "<random-token>": { "name": "Sales - Jane", "stores": ["gaf","revel"] }
}

// Connect (claude.ai / desktop GUI): paste as the connector URL
https://shopify-mcp.<account>.workers.dev/c/<token>

// Connect (Claude Code)
claude mcp add --transport http shopify \
  https://shopify-mcp.<account>.workers.dev \
  --header "Authorization: Bearer <token>"
Revocation. Remove a user's entry from USER_TOKENS and redeploy the secret — instant cutoff, no Shopify change. Adding a user is the inverse. Locking someone to one store is "stores":["gaf"].

6 Security model

The boundary: read-only, not narrow-scope

The Shopify custom apps carry broad read scopes (including customer data), and — by owner decision — the MCP exposes that full read surface to authorised users. So the model does not rely on hiding data; it relies on three guarantees:

  • No write path. Every tool is read-only. The generic shopify_query tool strips comments/strings and rejects any mutation or subscription operation, so the API cannot be driven to change anything.
  • Per-user identity & revocation. Access is keyed to a per-user token that can be revoked instantly without touching Shopify. Each token is scoped to specific stores.
  • Per-store gate. Every tools/call checks the requested store against the user's allowlist before any upstream call.
Customer personal data is in scope. Orders and customer tools return names, emails, phones and addresses. This is an accepted, deliberate decision — access should be limited to staff with a legitimate need, and the per-user token model is what enforces that.

Credential handling

  • Shopify client_id/secret and the USER_TOKENS map are Cloudflare Worker secrets — encrypted at rest, never in source.
  • Nothing secret is committed. Worker code/config are clean; local creds live in chmod 600 files outside the git repo; this public page uses placeholders only.
  • Minted shpat_ tokens are short-lived (24h) and never leave the Worker.

Residual risks (accepted / known)

  • Capability URL = bearer in a URL. Anyone holding the link has that user's access, so it is treated as a secret and is per-user revocable.
  • Broad read access incl. PII. An authorised user can read customer data; mitigated by limiting who gets a token and by the no-write guarantee.
  • No rate limiting or audit log yet (see future work).

7 Operations

Source lives in the vault at Agent/Scripts/shopify-mcp/ (worker.js, wrangler.toml, README.md). Deploy and secret management via Wrangler:

# deploy
cd Agent/Scripts/shopify-mcp
export $(grep -v '^#' ~/.cloudflare-env | xargs)
npx wrangler@latest deploy

# set / rotate a secret (reads from local chmod-600 creds files)
echo -n "$CLIENT_SECRET" | npx wrangler@latest secret put GAF_CLIENT_SECRET

# add or revoke a user = edit the USER_TOKENS JSON, re-put
echo -n '{...}' | npx wrangler@latest secret put USER_TOKENS

8 Future enhancements

  • OAuth 2.0 on the Worker → native, header-free connector auth in the claude.ai UI (replaces the capability URL).
  • Cloudflare Access in front → staff log in with their @gymandfitness.com.au Google account instead of a per-user token.
  • Audit logging (who called what, when) and rate limiting per user — especially relevant now PII is in scope.
  • Optional PII redaction mode per user/token, for staff who only need product/order operations.
  • KV-backed token cache for token reuse across Worker isolates.
