Standard Operating Procedure

Winnings SAP Order Entry

How Revel sales orders flow from NetSuite into the Winnings 3PL SAP system for dispatch — the process, the rules, and the safeguards.

Owner: AFS Group Operated by: Gary (AI Assistant) + CSR / Logistics Systems: NetSuite → Winnings SAP (VA01) Last updated: 17 June 2026 Live process

Purpose

Revel orders are created in NetSuite (the source of truth) and must be re-keyed into the Winnings 3PL SAP system as Standard Orders so the warehouse can pick, pack and dispatch. This SOP documents how that transfer is done accurately and safely, and mirrors the automation skill Gary runs. It is a transparent reflection of the process so the team can see exactly what is happening at each step.

How it works

The work is split so that the thinking is automated and the production system write stays supervised.

Step 1 — Request

An order list is raised in Asana

The CSR team tags Gary in an Asana card with the NetSuite sales orders that need entering into Winnings. Gary can also compile the list directly from NetSuite.

Step 2 — Prepare (automated)

Gary reads and validates each order

For every order, Gary pulls the details from NetSuite, pre-resolves the routine decisions, checks for duplicates, and flags any exceptions back on the card. No SAP access is needed for this stage.

Step 3 — Execute (supervised)

Orders are keyed into SAP, then checked

In a logged-in SAP session, Gary keys the batch one order at a time, pausing only on genuine exceptions. Every order is built and left for a person to review and save. Gary never saves to the production system on its own.

What gets mapped

Each NetSuite order becomes a SAP Standard Order (type ZWSO). The customer is never the SAP account — they are entered as a one-time delivery address.

SAP fieldWhere it comes from
Sold-To PartyFixed Revel account (pre-filled) — not the customer
Ship-To PartyOne-time delivery address built from the NetSuite shipping address
Customer ReferenceThe NetSuite sales order number — the link between the two systems
Requested Delivery DateThe order's expected delivery date (EDC)
Line itemsPhysical goods only (SKU + quantity); freight, deposit and balance lines are excluded
Weight / Volume / Plant / PricingDerived automatically by SAP — used as a cross-check, never overridden

Decision rules

QuestionRule
Delivery dateDefault to the next available delivery date. If the NetSuite memo notes a customer-requested date, use that. If that date isn't available, flag it on the Asana card rather than guessing. The date is set before items are added.
Is installation required?Yes only if the order has a Winnings Install line item. Otherwise No.
Australian phone numberUse as entered; normalise to local format if it carries the AU country code.
Which email?Use the main order email on the sales order.
Address formatSplit the street line into house number and street name (separate SAP fields).

Critical safeguard — incorrect contact numbers

▲ Foreign contact number (e.g. Hong Kong +852) — do not complete the order

A foreign phone number on an Australian Revel delivery is treated as an incorrect contact number. The order must not be keyed or saved into SAP with that number.

  1. Stop — do not complete the SAP entry.
  2. Flag it to the CSR team on the Asana card, noting that the contact number on the order is incorrect.
  3. CSR sources the correct Australian contact number.
  4. The order is only finished once a valid number is supplied. It is tracked as "blocked — awaiting contact number" so it is never lost.

Built-in checks

  • Ready to Send only: only orders flagged "Ready to Send" in NetSuite are in scope; orders not yet marked ready are left out of the work-list.
  • Ship Complete respected: orders flagged ship-complete are held out of the work-list until every line is available, so they are only entered when the whole order can ship together.
  • Duplicate guard: SAP blocks a sales order whose reference has already been entered, preventing double-keying. If flagged, the order is already in SAP and is skipped.
  • System prompts: expected SAP messages (oversized items, a known time-zone notice, installation question) are handled to a defined rule rather than guessed.
  • Cross-check: the weight, volume and warehouse SAP derives are compared back to NetSuite before the order is handed over for review.
  • No silent saves: orders are built and left at the save step for a person to confirm. Writing to the production system always has a human in the loop.

After an order is saved

Once an order is confirmed and saved, SAP issues an order number. That number is recorded against the original NetSuite order — this is both the record of completion and the marker that prevents the order being entered twice.
